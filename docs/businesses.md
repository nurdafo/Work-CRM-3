# Кабинеты бизнесов

Рабочая реализация: `web` (React) и `api` (FastAPI). `site` не изменяется.
Организации разделяют данные бизнесов. Новый бизнес получает основной проект и
владельца с ролью `ADMIN`. Роль `PLATFORM_ADMIN` управляет всей платформой.

## Обновление существующей установки

1. Сделайте резервную копию базы. Для SQLite используйте backup API SQLite, для
   PostgreSQL — `pg_dump`. Сохраните также серверные ключи в защищённом месте.
2. Обновите зависимости: `.\.venv\Scripts\python.exe -m pip install -r api\requirements.txt`.
3. Добавьте в корневой `.env` постоянный `INTEGRATION_ENCRYPTION_KEY`. Генерация:
   `.\.venv\Scripts\python.exe -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.
   Не заменяйте ключ при перезапусках: он нужен для расшифровки сохранённых токенов.
4. Из каталога `api` выполните:

   ```powershell
   ..\.venv\Scripts\python.exe -m alembic upgrade head
   ..\.venv\Scripts\python.exe -m app.migrate_businesses
   ```

   Перенос находит существующего администратора по `ADMIN_USERNAME`, проверяет
   организацию ADS.KZ, сохраняет настройки Meta зашифрованными и назначает роль
   администратора платформы. Пароль и заявки не меняются. Повторный запуск не
   перезаписывает подключения. Старые сеансы требуют повторного входа.
   Для пустой установки сначала выполните `python -m app.bootstrap`.
5. Перезапустите API и интерфейс. Войдите с логином `ADMIN_USERNAME` и текущим
   паролем; откройте «Бизнесы».

В локальной установке, обновлённой при реализации, ключ и миграция уже настроены.
При переносе на другой сервер переносите базу вместе с её ключом шифрования.

## Работа администратора

«Добавить бизнес» создаёт кабинет с названием, логином и паролем. Подключения
необязательны: до их настройки доступны ручные заявки. «Открыть CRM» переключает
контекст; «Все бизнесы» возвращает в общую панель. При переключении сбрасываются
карточки, фильтры и загруженные данные предыдущего кабинета.

Сохранённые токены не возвращаются в браузер. Пустое поле сохраняет текущий токен;
для удаления предусмотрен флажок. Сброс пароля отзывает сеансы владельца.
Отключение бизнеса отзывает сеансы всех его пользователей и приостанавливает
webhook и очередь. После включения нужен новый вход. Собственный бизнес
администратора платформы отключить нельзя.

Meta: Page ID, токен страницы, необязательный Form ID, Dataset ID и токен
Conversions API для качества. Рекламный аккаунт и его токен сохраняются отдельно;
проверка читает `account_id`, управление кампаниями и статистика не добавлялись.
Проверка токена страницы не заменяет проверку прав на лиды: для этого используйте
«Обновить из Meta». Одна страница не может принадлежать двум кабинетам.

После переноса глобальные ID страницы/формы, токены и настройки качества из `.env`
использует только команда первоначального переноса ADS.KZ. Операции CRM читают
настройки бизнеса из базы. Общими остаются версия Graph API, секрет приложения
и verify token подписанного Meta webhook.

Telegram требует bot token и chat ID. Проверка проверяет токен;
«Отправить тест в Telegram» проверяет доставку в выбранный чат. Используются
методы [getMe и sendMessage](https://core.telegram.org/bots/api).

## Очередь Telegram

Новые ручные и Meta-заявки создают запись очереди в той же транзакции, если бот и
чат настроены. API делает первую попытку после сохранения. Для повторных попыток
и восстановления после перезапуска запустите отдельный процесс из `api`:

```powershell
..\.venv\Scripts\python.exe -m app.telegram
```

Обе конфигурации Docker Compose включают `telegram-worker` с той же базой и ключом.
Для Vercel нужен отдельный постоянно работающий worker с доступом к PostgreSQL.

Повторные попытки идут с увеличением интервала до одного часа. Очередь сохраняется
в базе; повторный импорт Meta не создаёт уведомление повторно. Блокировка на пять
минут предотвращает одновременную отправку несколькими worker и восстанавливается
после сбоя. Если Telegram принял сообщение, а ответ потерялся, повторная попытка
может дать дубликат: `sendMessage` не предоставляет ключ идемпотентности.
Число неотправленных уведомлений видно в панели. Ошибки не содержат URL с токеном.

## API и проверка

- `POST /admin/businesses`: название, логин, пароль, необязательные подключения.
- `GET /admin/businesses`: кабинеты и признаки наличия токенов без самих токенов.
- `PATCH /admin/businesses/{id}`: название, логин, новый пароль, active, подключения.
- `POST /admin/businesses/{id}/check`: проверка сохранённых подключений.
- `POST /admin/businesses/{id}/telegram-test`: тестовое сообщение.
- CRM API принимают `X-Organization-ID`; выбирать чужой бизнес может только
  `PLATFORM_ADMIN`. Проверка принадлежности выполняется на сервере.
- `/auth/me` дополнен названием текущей организации и ID домашней организации.
- JWT содержит версию сеанса, которую изменяют сброс пароля и блокировка.

Из `api`: `..\.venv\Scripts\python.exe -m pytest tests -q`.
Из `web`: `npm test` и `npm run build`. Внешние сервисы в тестах имитируются:
реальные сообщения не отправляются, аккаунты Meta не изменяются.

Миграцию сначала проверяют на копии базы, сравнивая записи CRM и хеши паролей.
Для отката после начала работы сохраняйте полную резервную копию: новые кабинеты
и очередь не входят в старую схему.
